# 実装指示書：AI分析パック（Markdown出力機能）

> 「観測は続く。」に、**自分のnote観測データを ChatGPT/Claude/Gemini に貼れるMarkdownとして出力する機能**を追加する。
> アプリ内でAI分析はしない。**アプリは「AIに渡すためのMarkdown出力」に徹する。**
> ロジックは Python プロトタイプ `docs/analysis_pack_export.py`（このリポ内・計算ロジックの正本として参照）で検証済み。4つのAI（ChatGPT/Claude/Gemini/Grok）で有用な分析が返ることを確認済み。
> 方針：ジュリ最終判定（2026-06-27）。作成：澪。

---

## 0. 結論・責務（ブレ防止）

- これは「AI分析機能」ではない。**AIに渡すための観測データ出力機能**。
- お礼・スキ返しは既存の Today/Fans が担う。**重複させない。** これは「改善・気づき」用。
- 価値の核＝**noteの実データ（一次情報）をそのままAIに渡せること**。数字を弱めない。

| 担当 | やること |
|---|---|
| 観測は続く。（このアプリ） | データを収集し、Markdownに整形・出力する |
| 同梱プロンプト | AIへの分析観点と出力ルール（個人名保護など）を指定 |
| 各ユーザーのAI | 分析・仮説出し・振り返り下書きを生成 |
| ユーザー | AI出力を読んで、必要なら編集・公開 |

## 3. 生成するMarkdownの中身

**計算ロジック・列・フォーマットは `analysis_pack_export.py` を正本として移植**。以下は要点。

### 冒頭：注意書き（固定）
```
> このMarkdownは、ChatGPTやClaudeなどのAIに貼ってnote運営を振り返るための分析パックです。
> 個人別の反応履歴を含む場合があります。
> 公開記事などに使う場合は、AIの出力を確認し、個人名や個別履歴が本文に出ないよう編集してください。
```
- 補正スキ率の定義も明記：補正スキ率＝スキ÷公開当時フォロワー数（母数の罠を回避。履歴外はN/A）。

### ① 記事マスター（直近30日・表）
- 列：記事 / 公開 / スキ / コメ / マガジン / 当時フォロワー / 補正スキ率 / 24h初速 / 新規・常連 / 深さ
- 補正スキ率 = スキ ÷ 公開当時フォロワー数（followers.csv を公開日でルックアップ。履歴外は **N/A**）
- 24h初速 = 公開後24時間以内のスキ数（liked_at − published_at ≤ 86400秒）
- 新規/常連 = その記事にスキした人のうち、初反応がその記事＝新規／過去にも反応＝常連
- 深さ = スキ×1 + コメント×5 + マガジン追加×10

### ② いつ出会った読者が、今も来てくれているか（定着）
※見出しは平易に。中身は初反応月ごとに、人数・直近30日に再反応した人数・定着率。
- 初反応した月ごとに、人数・直近30日に再反応した人数・定着率。

### ③ 最近、来てくれなくなった常連
- 通算5回以上スキ かつ 直近30日無反応。名前・通算スキ・最終反応日。
- ※これはAI分析用の材料。**振り返りnote本文には個人名を出さない**（制御は下記プロンプトで）。

### 🤖 分析プロンプト（末尾に固定同梱）
1. **振り返り**：①を見て、補正スキ率・深さ・24h初速・新規/常連比から、刺さった型と空振りの型を各3つ（傾向で・優劣の断定はしない）。
2. **次の一手（主軸）**：②③から、来月書くと良いテーマ・切り口を3つ（新規を連れてくる型／常連が喜ぶ型で分けて）。
3. **振り返りnoteの下書き**：この分析を読者に見せられる振り返りnoteの下書きに。条件：
   - **数字は一次情報として明示する**（補正スキ率・深さ・24h初速・新規/常連比など根拠になる数値を必要な箇所で引用）。※「数字控えめ」とは書かない。
   - 数字の羅列でなく「数字から何が見えたか」まで書く。
   - **個人名・個別読者の通算スキ数・最終反応日は本文に出さない。** 必要なら「過去によく反応してくれていた読者層」など集計・傾向として扱う。
   - 推測は推測として書き、断定しすぎない。

## 8. ①の表の記事マーカー（追加仕様・2026-06-28）

### 背景

KOTAYAさん（kotaya_log）の出力で2つの構造問題が判明した：

1. **課金記事のコメ・深さが構造的に低く出る**：有料記事・メンシプ限定記事は、コメント可能な読者が購入者／会員に限定される。深さ式 `lk + cm*5 + mag*10` がコメに重み付けしているため、課金記事は無料記事と並ぶと「コメが少ない＝刺さってない」と誤読される。articles.csv には課金フラグがない。
2. **公開直後の記事の数字が育ち切っていない**：note-data-collector は4時間毎に動く。データ最新時刻時点でまだ伸び盛りの記事は、本来の数字より小さい状態でMarkdownに乗る。実例：「noteフォロワー3,000人」（kotaya_log・2026-06-27 20:30公開）は、CSV収集時点（経過2h）でスキ27・コメ10だったが、24時間後のAPI実測でスキ84・コメ44に伸びていた（約3倍）。

### 方針：**マーカーを付けるだけ。深さ式は触らない。注記もごちゃごちゃ書かない。**

数字補正はせず、課金記事には `💎` を、公開後72時間未満の記事には `🆕` を、判定取得に失敗した記事には `?` を付け、**AIに「数字が低い構造原因」を察してもらう**。これは「アプリは出力に徹する」設計原則の延長。

### 判定ロジック（最小）

#### 💎（課金マーカー）

`/api/v3/notes/{note_key}` を叩き、レスポンスの `data.price` を見るだけ。

```js
const isPaid = (data.price ?? 0) > 0;  // ← これだけ
```

検証済み（2026-06-28、KOTAYAさん3記事で確認）：
- メンシプ限定記事＝note内部仕様で `price > 0`（例：n12a8431dc240 / price=700）
- 有料記事＝当然 `price > 0`（例：n57cfd1c0e046 ※完売後はprice=0で要注意・本人判定でも誤検知あり）
- 通常記事＝`price = 0`

→ **有料／メンシプを分けず `💎` 一本で表現**（ユーザーの好み・AIに察させる方針）。

#### 🆕（伸び盛りマーカー）

`published_at` と「データ最新時刻」の差で判定。fetch 不要。

```js
const dataLatestMs = Date.parse(dataLatest + 'T23:59:59+09:00');  // 既存ロジックを流用
const pubMs = Date.parse(article.published_at);
const isFresh = pubMs != null && (dataLatestMs - pubMs) < 72 * 3600 * 1000;
```

閾値 **72時間**の根拠：
- noteのアルゴリズムは「公開後72時間が初速の勝負」が外部リサーチでの収束（4専門家・60_pickaxe候補参照）
- KOTAYAさん17本で実検証（2026-06-28・data_latest=2026-06-27 22:30）：24h閾値=1件 / 48h閾値=1件 / 72h閾値=2件 → 72hで「経過2hの6/27記事」と「経過50hの6/25記事（まだ伸びる）」を両方守れる
- 48hだと経過50h前後の記事（≒2日経過）が無印で出てしまう＝AIに「育った数字」と誤読される

#### 注意：💎と🆕は同時付与可能

両方該当する記事は `💎🆕 タイトル...` の順で並べる。

### fetch ポリシー（💎判定のみ・🆕はfetch不要）

- **対象**：①の表に出す記事（＝直近30日）だけ。②③のコホート計算には不要
- **直列600ms sleep**（並列はnoteレート制限リスク・速度差は「取得中…」表示でカバー）
- **失敗時は `?` マーク**（無印にして「課金ではない」と誤伝するのは避ける／詳細はコンソール warn）
- 🆕 は既存の published_at から計算するだけなので fetch には含めない

### Markdown 出力への反映

①の表の「記事」列、先頭にマーカー（💎🆕 の順、両方該当なら並べる）：

| 条件 | マーカー | 例 |
|---|---|---|
| price > 0 のみ | `💎 ` | `💎 メンシプ17人。残り83人を…` |
| 公開後72h未満のみ | `🆕 ` | `🆕 noteフォロワー3,000人。売上0円から…` |
| 両方該当 | `💎🆕 ` | `💎🆕 直近の有料記事タイトル` |
| いずれにも該当しない | なし | `note生態図鑑【創刊号】…` |
| fetch失敗 | `? ` | `? 取得失敗した記事タイトル`（🆕は通常通り付与） |

表の直下に凡例1行（注記でも分析の補正でもなく、**マーカーの意味の説明**）：

```
> 💎＝課金記事（有料／メンシプ限定）。コメント可能な読者が購入者・会員に限定されるため、無料記事と直接比較せず傾向で読んでください。 ／ 🆕＝公開後72時間未満。数字が育ち切っていない＝伸び続ける可能性があり、固まった数字として扱わないでください。 ／ ?＝判定取得に失敗。
```

### UX

- 「📋 直近30日のMarkdownを生成」ボタン押下後、**ボタンを「取得中…」表示にして disable**
- 17本前後で約10秒、最大30本で約20秒（直近30日上限）
- 取得完了したら通常通り `<textarea>` に流して `[コピー][.mdダウンロード][ChatGPTで開く][Claudeで開く]` を表示

### やらないこと

- 深さ式の補正（`depth = lk + cm*5 + mag*10` のまま）
- 「コメ少ない＝刺さってない」「数字が育ち切ってない」のためのプロンプト追加注記（マーカーで察させる）
- データ層（articles.csv等）の改修
- 有料／メンシプの区別表示（💎一本に統一）
- ②③のコホート計算や churn 判定への課金判定・🆕判定の混入
- 🆕記事の除外（直近30日内なら、伸び盛りでも全部表に含める）

### Python正本（analysis_pack_export.py）への反映

ロジック正本としての一致性を保つため、Python側も同じ判定を行う：

- 💎：各対象記事について `urllib.request` で `/api/v3/notes/{key}` を叩く（`User-Agent: Mozilla/5.0` ・ `Accept: application/json` ・ 0.6秒sleep）。`data.price > 0` で `💎`、失敗時は `?`
- 🆕：`data_latest`（likes.csv の最新 liked_at 日付の23:59:59 JST）と `published_at` の差が72時間未満なら `🆕`。fetch不要
- 両方該当なら `💎🆕 ` の順

→ 完了条件の「数値一致検算」が引き続き成立する。
